# POS administration

`CLAUDE.md` imports this file. This standalone Vite + React app administers POS
configuration and hosts the back-office operations: orders, deliveries, funds,
shift management, receivables, reports and inventory traceability. Counter work
(selling, returns/exchanges, receipt printing, collecting debts into a drawer, a
cashier's own shift) stays in `apps/pos`; do not add it here.

## Run and verify

Run the API through `pnpm spree dev --no-open` from the repository root. Never
invoke Rails, Ruby, rake, bundle or Docker Compose directly. In this directory:

```sh
pnpm install
pnpm dev             # strict port 5176
pnpm typecheck
pnpm lint
pnpm test
pnpm build
pnpm test:e2e        # API fixtures, desktop/tablet/mobile; 4 workers
```

## Structure and integration contract

- `src/routes/`: TanStack file routes and access guards. `routeTree.gen.ts` is
  generated by Vite's router plugin; do not hand-edit it.
- `src/pages/`, `components/`, `tables/`, `schemas/`: resource UI, reusable controls,
  table definitions and form schemas respectively.
- `src/hooks/`: Admin API wrappers. Use `posRequest`, which delegates to the
  registered `adminClient.request`; never use POS session coordinator or fetch
  directly. All query keys begin `['pos', storeId, resource, ...]`.
- `src/lib/pos-access.ts`: store permission keys + selected-branch capability gates.
  Each protected route must use `PosRouteGuard`; hiding nav is not authorization.
- `src/nav.ts`: registrations only, synchronized from the same access predicates.
  6.0.3 has no sidebar headings and no `if` on children or `settingsNav`, so groups
  are parent entries holding only the visible children; empty groups are not registered.
- Operational pages act on the selected branch (`context.data.selection.branch_id`),
  show `BranchPicker` in the page header and gate on that branch's capabilities.
- A branch's settings are the tabs of `/branches/$branchId` (`BRANCH_TABS` in
  `pos-access.ts`, `useBranchScope()`); the selection follows that URL. The
  Features tab groups industry modules, risky feature flags and per-branch
  `sales_settings` (stock display, oversell, notes, coupons, cart order,
  payment sound, receipt auto-print). Seeing cost needs `pos.cost.view`.
  Store
  master data (print templates, payment methods, units, staff roles, scale label
  formats) are store-level pages; old store-level setting URLs redirect to tabs.
- `src/i18n.ts`, `locales/{vi,en}.json`: every visible string is translated.
  POS keys are registered in both `translation` and `pos`; shell keys live under
  `posDashboard`. Core i18next initialization must not be replaced.

Import framework components/providers from `@spree/dashboard-core`, controls from
`@spree/dashboard-ui`. Keep core/ui/admin-sdk pinned together at **6.0.3**.
Screen layout follows `DESIGN.md`: pill tabs, and a section title with an icon
above the card.
Pure POS logic comes from `@parkviet/pos-shared/<module>`; shared data types are
under `@parkviet/pos-shared/types/pos-context` and `types/print-adapter`.

Use `usePosSession()` inside the store shell for `{context, selection, setSelection}`;
`context` is a React Query result, selection is `{branchId, registerId}`. Explicit
`usePosContext(selection)` and `useBranchSelection(branches)` are also available.
The context API returns **bare** JSON, while list/mutation endpoints generally
return `{data, meta}`. Never blindly unwrap every SDK response.

The store SDK header is set in route `beforeLoad`, before child queries run.
PermissionProvider mounts **inside** StoreProvider. Do not move it above the store
or reuse a previous store's permissions. Auth uses refresh cookies, not localStorage
tokens; logout clears the framework query cache.

Writes use `useMutation`/`useResourceMutation`; preserve 409 reason and 422 field
details so shared failure helpers and `mapSpreeErrorsToForm` still work. Destructive
click actions need `useConfirm({variant:'destructive', ...})`. Invalidate the current
store's POS keys after writes. Never embed SDK entity types inside form-value types.

## Home widgets ("Tổng quan")

The home page (`src/pages/home.tsx`) is a 12-column `react-grid-layout` board
(64px rows, 8px gaps) of widgets registered in
`src/components/home-widgets/registry.tsx` (`HOME_WIDGETS`, default order in
`HOME_DEFAULT_WIDGETS`). To add a widget, add a `WidgetDefinition` there:

- `widget`: a stable kebab-case id (`/^[a-z0-9_-]{1,64}$/`); it is stored in
  layouts, so never rename it. `titleKey`/`hintKey` are i18n keys in both locales.
- `size`: default `w`/`h` and `minW`/`minH`/`maxW`/`maxH` in grid units.
- `visible(access)`: the branch capability gate; a widget that does not apply
  keeps its slot but is not shown. `unavailable(overview)` hides it when the
  loaded overview has nothing for it.
- `usesOverview: true` when it reads `useOverview`; the page fetches the
  overview only while such a widget is on it. Links go through `lib/home-links.ts`
  so drill-downs carry the page's `from`/`to` with the target page's search keys.

Placement rules are pure functions in `src/lib/dashboard-layout.ts`. Each user's
layout is stored per store through `GET`/`PUT`/`DELETE /pos/dashboard_layout`
(`hooks/use-dashboard-layout.ts`; no row means the registry default, and
confirming the default deletes the row). The server checks shape only: at most
50 items, `h` ≤ 20, row ≤ 1000, `options` ≤ 2 KB, id/widget formats; keep the
client constants in `dashboard-layout.ts` in step with
`Spree::Pos::DashboardLayout`. Sales widgets read
`GET /pos/overview?branch_id&from&to&compare=1` (types in
`@parkviet/pos-shared/overview`). Narrow screens stack the widgets in one column
without grips or resize corners. `e2e/home.spec.ts` covers drag, resize, hide,
add, cancel, reset and drill-downs with route mocks.

Store information lives at `/settings/store-info` (`pages/store-info.tsx`) and is the
first item of the Thiết lập sidebar, above Chi nhánh. Its path is store-root
relative (`/settings/store-info`); settings-nav paths are relative to `/settings`
and must not include that prefix. The page stays on the main sidebar, like
receipt templates.
It holds the POS name, contacts, logo, business types, opening hours, business-day
cutoff and the two-level Vietnam address. `/settings/business-model` redirects
there. A branch copies those values and overrides them on its Information tab
(`components/branch-info-card.tsx`). New branches take the store's business types;
the first selected type is the primary one.

Tax declaration info lives at `/settings/tax-info` (`pages/tax-info.tsx`), directly
under store information in the sidebar, behind the same access rule. It reads and
writes `GET`/`PATCH /pos/tax_profile`: the taxpayer name, tax code, address and
description are the store information's own fields (never copied), and branches
appear as business locations (location code, one head office). Its pickers read
`GET /pos/tax_catalog` (`server/config/pos/vn_tax_catalog.yml`).

Tax configuration lives at `/settings/tax` (`pages/tax-config.tsx`, key `tax`, shown
and reachable to topology writers only, as the API serves no one else). It reads `GET /pos/tax_regime`, saves with `PUT` and previews
the unsaved draft with `POST /pos/tax_regime/preview` (debounced; the server computes
every amount, the page only formats them). Which methods, income tax methods and options
a revenue group allows comes from that state, never from constants; pure draft logic is in
`schemas/tax-regime.ts`. Changing the method, or a default option, asks for confirmation
first (`components/tax-config-confirm.tsx`, with "apply to all products" for defaults).

## Goods ("Hàng hoá")

The Goods group (`/goods/*`; `/products` stays the redirect to the branch
Products tab) manages the store's Spree catalog: products, barcode labels,
ingredients, price lists, categories, add-on groups and recipes. Products are
Spree records read and written through `adminClient.<resource>`
(`hooks/use-goods.ts`, keys `['pos', storeId, 'goods', ...]`); there is no POS
product table. Gates in `pos-access.ts` use the staff role's catalog keys:
`read_products`/`write_products` (products, ingredients, price lists, labels),
`read_categories`/`write_categories`, and `write_settings` to create the `pos`
channel; add-on groups and recipes keep the menu and recipe gates. Before a
save, `hooks/use-goods-setup.ts` ensures the `pos` channel (created active, not
default, never re-activated) and the product types `Hàng hoá`, `Dịch vụ`,
`Nguyên liệu`, recognized by name without marks or case. Never ensure them on
read. Each nav child is added to the `goods` group in `nav.ts` with its page.

Products (`pages/goods-products.tsx`, `pages/goods-product-form.tsx`, pure
mapping in `lib/goods-products.ts`, save sequence in `hooks/use-goods-products.ts`)
list `GET /products` with two server scopes from `server/app/models/spree/product_decorator.rb`:
`q[search_with_barcode]` (name, SKU or barcode) and `q[not_in_channel]=pos` (the
"not on POS yet" view). Units per row come from `GET /pos/units/variants`, and a
product's branches from `GET /pos/branches/:id/products?product_id=`. An edit
never sends `stock_levels` (the API removes locations left out); a create that
saved the product but failed a later step (branches, unit, image) is retried by
saving again, which patches instead of creating a second product.

Attributes are Spree option types (`lib/goods-variants.ts`): before a save the
form makes each attribute and value exist (named by an ASCII slug, shown by its
label; an update sends the type's whole value set back) and variants name them
in `options`. A new product is priced per variant, never with product-level
`prices`. An edit keeps attribute names, sends kept variants with the product
`PATCH` (with the variants to remove as bare ids, since that update replaces the
variant set), then deletes and creates variants through `/products/:id/variants`; a
refused delete (variant on orders, or an ingredient of an active recipe) is a
reported follow-up step, and a variant already gone counts as deleted. A simple product
given attributes turns its single variant into the first combination. A
prepared product ("Sản phẩm chế biến") also carries POS operating data keyed by
its id, read from `GET /pos/products/settings` (every prepared product of the
store) and shown only where the add-on groups page is
and only while the form's kind is prepared: the "Vận hành" block (kitchen
category, cup label, contents on the kitchen screen, QR ordering, drink credit)
saved with `PUT /pos/products/:id/settings`, add-on groups with
`PUT .../modifier_groups` and combo contents with `PUT .../combo` (pure rules
and the write plan in `lib/product-operations.ts`). Only changed parts are
written, after the product and its branches; a combo takes no add-on groups, so
the clearing write goes first. "Copy from another product" fills the block,
groups and combo from another prepared product (Spree's duplicate and CSV import
carry no POS data). Tax is set on each product in this form. The server never adds a product to a branch: the branch
checklist (all active branches by default, for topology writers) is what makes a
new product sell at the till. Unit conversion opens the
branch `VariantUnitEditor` through a branch selling the product. The price-list
card writes Spree prices (`/prices/bulk_upsert`, `bulk_destroy`, `min_quantity`
breaks on lists with a volume rule) on its own and refreshes only price reads.

Barcode labels (`pages/goods-barcode-labels.tsx` at `/goods/barcode-labels`, pick rules
in `lib/goods-barcode-labels.ts`, reads in `hooks/use-goods-barcode-labels.ts`) pick
variants sold at the selected branch from `GET /pos/catalog` (search, or Enter in the
search box: an exact `barcode=true` hit is added, again for one more label) and set a
count per row (0 leaves a row out; "by stock" keeps rows without stock unchanged). The
selling price is the variant's base price (`/prices`, `price_list_id_null`); the
catalog's POS channel price shows as the promotional price when a price list changes
it. Printing opens the shared `components/product-label/print-labels-dialog.tsx`, which
owns templates, label stocks, barcodes and the print station; this page adds none.
The list belongs to one branch and is cleared when the branch changes.

Price lists (`pages/goods-price-lists.tsx`, `pages/goods-price-list-form.tsx` at
`/goods/price-lists/new` and `/$priceListId`, pure rules in `lib/goods-price-list-form.ts`,
reads and saves in `hooks/use-goods-price-lists.ts`) are Spree price lists. The tabs
count states from `status`, `starts_at`, `ends_at` (an end in the past is expired
whatever the status). The code is the list's `description` (Spree has no code or
metadata field; generated codes are `BG` and six digits). A list for all customers
carries a `channel_rule` (the `pos` channel by default, ensured on save) and, for
wholesale, a `volume_rule`; the payload sends the whole rule set, keeping rule ids
and rules the screen does not manage. A customer-group list is the price list of a
catalog created with `metadata.pos_price_list = true` and assigned to the groups;
it is read through `/catalogs` and cannot switch audience once a save has written
it. New lists are activated; a save that failed after creating the list (or its
catalog) is retried without creating a second one, and still activates it. Formula pricing only writes `prices` (bottom rung) from the selling price
when products are added or "Apply formula" is pressed. Prices per product use the
product form's `ListPriceDialog`. Channels need `read_settings`, groups `read_customers`.

Categories (`pages/goods-categories.tsx`, tree helpers in `lib/goods-categories.ts`,
save sequence in `hooks/use-goods-categories.ts`) are Spree `/categories`, shown
in tree order (`lft`) as a list or a grid (`?layout=grid`). Order moves a category
among its siblings with `PATCH /categories/:id/reposition` (0-based index); a
parent change also goes through reposition, since a plain update cannot move a
category to the top level. Members are written only with `POST`/`DELETE
/categories/:id/products`; a save that failed after creating the category is
retried without creating a second one. Deleting a category also deletes the ones
under it and keeps the products; `products_count` includes subcategories.

Ingredients (`pages/goods-ingredients.tsx`, drawer in
`components/goods-ingredient-sheet.tsx`, mapping in `lib/goods-ingredients.ts`,
save sequence in `hooks/use-goods-ingredients.ts`) are products of the
`Nguyên liệu` type (`q[product_type_id_eq]`), tracked, on no channel, so no
branch assortment holds them; the products list's "not on POS yet" view leaves
them out with a Ransack `or` group that keeps untyped products. The whole list
is read and filtered locally for the selected branch's selling location.
Generated codes are `NL` and six digits. A create sends opening `stock_levels`
for every distinct branch location; an edit never does. The stock unit is
`PUT /pos/units/variant` without `branch_id` (catalog writers, canonical unit
at 1:1, refused once stock or a recipe counts in it), and the low-stock
threshold is the selected branch's `PUT /pos/stock_alerts`, offered while it
runs recipes. The server refuses to delete a product or a variant an active
recipe uses (also when a product update leaves the variant out); a bulk delete
reports how many products it refused.

Add-on groups (`pages/goods-addons.tsx`, pure rules in `lib/goods-addons.ts`) are
the store's `modifier_groups`. `components/addon-group-dialog.tsx` is the one
group dialog: three switches map to the stored
limits (required is `min_select` ≥ 1, several options is `max_select` ≥ 2, more
than one of an option is `allow_quantity`, only with several options), each
option has a price, its own cost and in stock (`active`; the counter leaves an
option out of stock out), and the products are the store's prepared products
(combos excluded), whose groups are replaced with
`PUT /pos/products/:id/modifier_groups`. Option costs come only to menu or stock
managers; a row read without `cost_price` never sends one, so the stored cost stays. The server copies
an option's cost onto a sold line only when no active recipe or stocked variant
counts what it uses; the copy feeds the menu margin report and the below-cost
warning.

Recipes (`pages/goods-recipes.tsx`, drawer in `components/goods-recipe-sheet.tsx`,
pure rules in `lib/goods-recipes.ts`) list `GET /pos/recipes/list` (the store's
active recipes of variants and add-on options, `q`, `owner_type`, `variant_ids`,
paged, with each one's estimated cost) and read and write one recipe with the
existing `GET`/`PUT /pos/recipes`, the same calls as the menu screen's
`RecipeEditor`; both save through `useConfirmedRecipeSave` (a size with stock
asks before it is written off) and deleting saves an empty list. The drawer picks
a selling variant of any non-ingredient product and adds ingredients from the
ingredient products. "Cost from ingredients" then sets the variant's
`cost_price` with `PATCH /products/:id/variants/:id` from the server's
`estimated_cost`, rounded to two decimals; it needs `write_products`. The
route needs `canManageRecipes`; the nav item also needs the selected branch to
run `fnb.recipes`. A recipe saves while any active branch runs the module, and
ingredients are taken from stock only at branches that run it.

## Menu ("Thực đơn")

The menu screen (`pages/menu.tsx`, reads and writes in `hooks/use-menu-admin.ts`)
operates what the store already sells; it manages no products, categories or
add-on groups and links to Goods for them. The till's tabs are the products'
Spree categories. It holds the store's combos (prepared products with contents,
edited with `components/goods-combo-editor.tsx` like the product form; making a
combo clears the product's add-on groups, "Bỏ combo" sends no contents) and
time-of-day menus (`/pos/menu_schedules`, rows by `product_id`), and for the
selected branch, from `GET /pos/menu`, the favourites row
(`PUT /pos/menu_favorites` with `product_ids`), today's sold-out marks
(`PUT /pos/menu_availabilities` with `product_id`) and each product's recipes.
The e-menu tab of a branch places prepared products by `product_id`.

Do not edit `apps/dashboard`. POS administration lives only here: do not add
settings or setup screens back to `apps/pos`.
